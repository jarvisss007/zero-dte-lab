## Today's calls: NONE — and the reason is my own contamination, not the tape
`ZDTE-004` (ruled 08-29) physically reordered the steps so the call is made **before
anything reads a live price**. I broke that this run — not by scoring first, but by
`tail`ing `data/chains/recorder.log` while establishing the first-snapshot time. **Every
line of that log prints `spot`**, so it handed me the entire 09:50→11:30 price path before
the call step. The same hole exists in the chain CSV itself: `spot` is a column on all 22
snapshots, so any read of the file below the first snapshot exposes the session path.

So: **no `implied_move` row and no `max_pain` row today.** Not because the day is
unreadable — it is unusually readable, and that is exactly the problem. The reordering fixed
step ORDER; it did not fix which SURFACES leak a price, and a call logged now would be
conditioned on two hours I should not have seen. This is the `ZDTE-002` selection argument
in its sharpest form: I know today's morning was quiet, `inside` would very likely score
`right`, and logging it would put a free win in the ledger by selection rather than skill.
Refusing costs the lab a probable `right`. That is the correct direction to err.

The operational fix is one line and I am proposing, not shipping it: **the first-snapshot
time is obtainable from the CSV's `fetched_at_et` column alone** (I did read it that way
first — the log tail was gratuitous). Guard: `recorder.log` is never read before the call
step, and `implied_density.py --time <first>` is the only price surface the call step
touches. No bar, no threshold, no definition changes.
